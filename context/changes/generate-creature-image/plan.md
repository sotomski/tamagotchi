# Generated Creature Image at Birth — Implementation Plan

> **Re-planned 2026-07-02 (raster pivot).** The original plan generated a
> char-grid `CritterSpec` via a Mistral structured-output call and rendered it
> with a Flutter `CustomPainter`. Extensive probing showed char-grids (Mistral and
> every Gemini text model) top out at unacceptable quality. This plan replaces the
> whole approach with a **raster JPEG generated by `gemini-3.1-flash-lite-image`,
> stored in Serverpod `public` DB storage, and rendered with `Image.network`.**
> See `change.md` → "PIVOT: raster image via Gemini". The superseded char-grid
> commits (`1f92481`, `a4fe1dc`, `b06c47b`) are walked back by Phase 1 below.

## Overview

When a creature is born (hatch), the server generates a unique retro pixel-art
body for it via a **blocking `gemini-3.1-flash-lite-image` HTTP call** (raw REST,
like the Mistral narrative path), stores the returned JPEG in Serverpod's `public`
database cloud storage, and persists the resulting **public no-auth URL** as a
`String?` field on the `Creature` row. The Flutter web client renders it with
`Image.network`. Scope is the **static** birth graphic only — no reaction
animations, no video.

## Current State Analysis

The hatch flow is a tight, deliberate sequence
(`tamagotchi_server/lib/src/creature/creature_endpoint.dart:28-139`):

1. Roll personality modifiers (`:46`).
2. **Blocking** narrative LLM call *before* the transaction
   (`hatchLlmServiceFactory(session).generateInteraction(...)`, `:55-70`). On
   throw it raises `CreatureHatchError(reason: narrativeUnavailable)` and nothing
   is written — deliberately **no canned fallback** (`hatch_copy.dart`).
3. A single `session.db.transaction` (`:74-116`) inserts `Creature`,
   `CreaturePersonality`, and a `hatched` `JournalEntry`.
4. Returns `CreatureStatus` via `_statusFor(creature, loveRegenMod)` (`:138`).

Reusable conventions already in place:

- **Service factory seams**: `hatchLlmServiceFactory = llmServiceFor` (`:702`);
  the same `<x>ServiceFactory = <x>ServiceFor` pattern exists for feed/play/cure.
  Tests reassign the seam and restore it with `addTearDown`
  (`creature_endpoint_test.dart:119-120`).
- **Key-presence stub selection**: `StubLlmService` is chosen when the key is
  absent (`llm_service.dart:96-113`). `test`/`e2e` omit `mistralApiKey` — and will
  likewise omit `geminiApiKey` — so they stay hermetic on the stub.
- **Serverpod `public` DB storage is already wired.** The `Serverpod` constructor
  registers `DatabaseCloudStorage('public')` and `('private')` by default
  (`serverpod-3.4.8/.../serverpod.dart:563`), and auto-registers
  `CloudStoragePublicEndpoint` whenever a DB storage exists (`:697`). So
  `session.storage.storeFile(storageId:'public', …)` and `getPublicUrl(...)` work
  with **no `server.dart` change**. `getPublicUrl` returns
  `<apiServer.publicScheme>://<publicHost>:<publicPort>/serverpod_cloud_storage?method=file&path=…`
  (`database_cloud_storage.dart:51`), served **without auth**.

Client render surface:

- `CreatureView` is a text/stat `Column` (`creature_view.dart:32-181`); the sprite
  slot is after the mood label (`:68`). The current `CritterImage`
  (compositor + `CustomPainter`) is **removed** in Phase 1 and replaced by an
  `Image.network` widget of the same name.
- `creatureProvider` returns `Future<CreatureStatus?>`; widget tests override it
  with canned values (`creature_view_test.dart`).

Personality is stored as **7 decay/regen multipliers in `[0.5, 1.5)`**
(`creature_personality.spy.yaml`, rolled in `creature_service.dart:53-67`). The
existing `critterVisualHints` mapping (`llm/critter_image_prompt.dart:38`) already
turns four of these axes into visual descriptors and is **kept** as-is.

## Desired End State

Hatching a new creature runs a blocking Gemini image call; on success the JPEG is
stored in `public` DB storage and its no-auth URL is persisted on the creature,
which the app renders with `Image.network` immediately after birth. On failure the
hatch fails cleanly (`CreatureHatchError(imageUnavailable)`) and nothing is
persisted — same contract the narrative call follows. Pre-existing creatures
(null `imageUrl`) render gracefully with no sprite.

### Key Discoveries

- `public`/`private` DB storage + the serving endpoint are **auto-registered** —
  no `server.dart` change (`serverpod.dart:563,697`).
- `getPublicUrl` bakes in `config.apiServer.publicHost/Scheme/Port`; per-env DBs
  keep dev (`localhost:8080`) and prod URLs isolated, so storing the **full URL**
  at hatch time is safe.
- `gemini-3.1-flash-lite-image` returns base64 JPEG in
  `candidates[0].content.parts[*].inlineData.data`; the request adds
  `generationConfig:{responseModalities:['IMAGE'], imageConfig:{aspectRatio:'1:1',
  imageSize:'1K'}}` for a **square 1024×1024** output (512 is unsupported; 1K is
  the model minimum, kept as-is — no downscale).
- Apply migrations with `serverpod run start`, **not** `--apply-migrations`
  (`context/foundation/lessons.md`).
- Run `dart format .` in both packages before each phase commit — Format CI is
  `--set-exit-if-changed`.

## What We're NOT Doing

- No reaction animations, motion presets, particles, or **video** (Veo explored
  and ruled out — cost/latency/aspect).
- No char-grid / `CritterSpec` / `CustomPainter` — deleted.
- No downscale / PNG re-encode / background chroma-key — the raw JPEG is kept.
- No object storage (GCS/S3) — Serverpod `public` DB storage only (user decision).
- No async/background generation — blocking at hatch, like the narrative call.
- No personality-axis refactor — `critterVisualHints` is reused unchanged.

## Implementation Approach

Three phases, each leaving **both packages compiling and all tests green** so the
per-phase commit gate holds:

1. **The rename (demolition + skeleton).** Rip out every char-grid artifact
   (server + client + the uncommitted Phase-3 files), swap the `Creature` field to
   `imageUrl: String?`, reimplement `CritterImage` as `Image.network`, regenerate
   and migrate. Nothing generates an image yet, but the whole repo is green on the
   new shape.
2. **The Gemini generate service.** Add `CritterImageService` (interface + real
   `gemini-3.1-flash-lite-image` impl + hermetic stub) behind the factory seam,
   plus the raster prompt builder. Unit-tested, not yet wired to hatch.
3. **Wire into hatch + storage + end-to-end.** Pre-generate the creature id,
   call the service before the transaction, store the JPEG in `public` storage,
   persist the public URL, block the hatch on failure, clean up the blob on reset.
   Integration-tested and manually verified in the running app.

## Critical Implementation Details

- **Timing & lifecycle**: the image call + store sit **outside and before** the
  `session.db.transaction` (alongside the narrative call), so any failure throws
  before rows are written — preserving "no half-hatched creature". Persist
  `imageUrl` **inside** the transaction as part of the `Creature` insert.
- **File key**: pre-generate `final creatureId = UuidValue.fromString(const Uuid().v7())`
  before the transaction; store the JPEG at `creatures/$creatureId.jpg` and set
  `Creature(id: creatureId, imageUrl: url, …)` explicitly on insert. This ties the
  blob to the creature and lets `reset` delete it deterministically.
- **Bytes**: `generateImage` returns `Uint8List` (raw JPEG); store via
  `session.storage.storeFile(storageId:'public', path:…, byteData: ByteData.view(bytes.buffer))`,
  then `getPublicUrl` (throw `imageUnavailable` if either fails or the URL is
  null).
- **Web CORS caveat (verify in Phase 3)**: the Flutter web app (served under
  `/app` on the web server) and the image URL (api server, `:8080`) can be
  different origins. Serverpod sends permissive CORS headers on API responses, so
  `Image.network` should load — confirm during manual testing; if a CanvasKit
  taint appears, that's the one thing to revisit.

## Phase 2: Gemini Generate Service (raster)

### Overview

Add the image-generation service behind the established factory seam: a real
`gemini-3.1-flash-lite-image` HTTP impl and a hermetic stub, plus the raster
prompt builder. Unit-tested; not yet wired to hatch.

### Changes Required

1. **Service interface + factory** (`lib/src/llm/critter_image_service.dart`):
   `abstract interface class CritterImageService` with
   `Future<Uint8List> generateImage(Session, CritterImageRequest)` (returns raw
   JPEG bytes — storage is the endpoint's job, keeping the service a pure
   bytes-producer like `LlmService`). Factory
   `critterImageServiceFor(Session) -> StubCritterImageService` when
   `geminiApiKey` absent/empty else `GeminiCritterImageService`, plus
   `critterImageServiceForKey(String?)` for unit tests (copy the shape of
   `llm_service.dart:96-113`).
2. **Real impl** (`lib/src/llm/gemini_critter_image_service.dart`): POST to
   `https://generativelanguage.googleapis.com/v1beta/models/gemini-3.1-flash-lite-image:generateContent`
   with header `x-goog-api-key`, body `{contents:[{role:'user',parts:[{text: prompt}]}],
   generationConfig:{responseModalities:['IMAGE'], imageConfig:{aspectRatio:'1:1',
   imageSize:'1K'}}}`;
   parse `candidates[0].content.parts[*].inlineData.data` (base64) → `Uint8List`.
   **Throw** on non-2xx or missing image (block-hatch posture). `completeForKey`
   seam for tests.
3. **Prompt builder** (extend `lib/src/llm/critter_image_prompt.dart`):
   `buildCritterImagePrompt(CritterImageRequest) -> String` — one text prompt:
   retro 16-bit pixel-art sprite, ONE cute original monster, chunky hard-edged
   pixels, bold dark outline, small palette, the creature **fills the square frame**
   (body nearly touching all four edges, thin uniform white margin, tightly
   cropped/zoomed), **pure solid white (#FFFFFF) background, one creature only, no
   shadow/ground/text/border**; weave in `critterVisualHints(req.personality)` and
   the variety `seed`. Pure, unit-testable.
4. **Stub + placeholder asset** (`lib/src/llm/stub_critter_image_service.dart`,
   `critter_image_copy.dart`): stub returns a small **valid placeholder JPEG**
   (base64 const in `critter_image_copy.dart`) so `test`/`e2e` hatches succeed;
   never throws.

### Success Criteria

#### Automated Verification

## Phase 3: Wire Into Hatch + Storage + End-to-End

### Overview

Insert the blocking generation + store into hatch, persist the URL, block on
failure, clean up on reset, and prove the full birth→render path.

### Changes Required

1. **New error reason** (`lib/src/creature/creature_hatch_error_reason.spy.yaml`):
   add `imageUnavailable` (regenerate).
2. **Factory seam** (`creature_endpoint.dart`): add
   `critterImageServiceFactory = critterImageServiceFor` next to
   `hatchLlmServiceFactory`.
3. **Hatch wiring** (`creature_endpoint.dart` `hatch`): after the narrative
   try/catch and before the transaction —
   pre-generate `creatureId`; `try { final bytes = await
   critterImageServiceFactory(session).generateImage(session, _imageRequest(...));
   await session.storage.storeFile(storageId:'public',
   path:'creatures/$creatureId.jpg', byteData: ByteData.view(bytes.buffer));
   final url = await session.storage.getPublicUrl(storageId:'public',
   path:'creatures/$creatureId.jpg'); if (url == null) throw …; } catch → log +
   throw CreatureHatchError(imageUnavailable)`. Build `CritterImageRequest` from a
   `CreaturePersonality` constructed from `mods` (creatureId + a fresh seed). Add
   `id: creatureId, imageUrl: url.toString()` to the `Creature` insert.
4. **Reset cleanup** (`creature_endpoint.dart` `reset`): before/around the delete,
   best-effort `session.storage.deleteFile(storageId:'public',
   path:'creatures/${creature.id}.jpg')` (don't fail reset on a storage error).
5. **Tests** (`test/creature/creature_endpoint_test.dart`): reassign
   `critterImageServiceFactory` to a valid-bytes fake and to a throwing fake, each
   with `addTearDown` restore. Assert: success → `creature.imageUrl` non-null and
   fetchable; failure → `CreatureHatchError(imageUnavailable)` and empty
   creature/personality/journal tables.

### Manual Testing Steps

4. Force a generation failure; confirm the hatch fails cleanly.

## Performance Considerations

Hatch now makes **two** sequential blocking external calls (narrative + image),
roughly doubling worst-case birth latency and failure probability, plus one DB
write of ~300 KB to `serverpod_cloud_storage`. Consider a modest timeout on the
Gemini call so a hung request fails fast. JPEG bytes are base64-inflated ~33% in
the DB (~400 KB/row) — negligible at this scale.

## Migration Notes

Drops the `creature.image json` column (added by `a4fe1dc`) and adds
`creature.imageUrl text` (nullable). The single existing dev creature loses its
(char-grid) image and renders without a sprite until re-hatched. No data backfill.
Apply with `serverpod run start`.
